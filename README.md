# USTP Job Order Renewal Portal

A working applicant and HRMO portal backed by PostgreSQL. The original design mockups remain under `/preview/...`; the live application is at `/`.

## What works

- Applicant registration and sign in with hashed passwords and eight-hour HTTP-only cookie sessions.
- An eight-step applicant workflow: Personal, Education, Contract, TOR, Compensation, Contact, Office, Review. New applications follow the supplied October–December 2026 Google Form PDF. Progress is saved between steps and resumes when a draft is reopened.
- New forms accept up to 30 numbered TOR duties. Previously saved applications retain their structured TOR editor and original fields.
- Optional PDF/PNG/JPEG supporting uploads (5 MB each, 10 per application).
- New forms collect separate name parts, date of birth, sex, civil status, address, USTP/PRC IDs, degree and eligibility details, contract dates, daily rate, contact and government numbers, supervisor/position, and a managed office choice. Required nonapplicable fields accept N/A where indicated. Submitted applications are locked to applicants. Daily rate words are calculated from the numeric amount.
- HRMO queue, document downloads, review, approval, rejection, and return for corrections.
- HRMO SQL database backup downloads and guarded restore with automatic recovery copies.
- HRMO office directory (add/deactivate/reactivate), applicant CSV import analysis and user management with password reset emails.
- HRMO shared contract settings hold university signatories and the signing date for new forms; no university names are prefilled.
- Approved applications can have a contract PDF generated by HRMO, with private downloads for HRMO and the applicant.
- Correction/resubmission and persistent status history. Concurrent edits are rejected with a refresh message.

## Docker deployment

Use the included `Dockerfile` and `compose.yaml` to run the portal and PostgreSQL with persistent volumes. See [the Docker deployment guide](deploy/README.md) for private configuration, first HRMO account creation, existing-record migration and the optional HTTPS setup.

## Development

Requirements: Node 24, pnpm, PostgreSQL 17, and Python 3.13+ with PyMuPDF 1.28.2 (declared in pyproject.toml). Install with `pnpm install --frozen-lockfile`.

For contract generation, create a Python virtual environment and set `PDF_PYTHON` on the API process:

```sh
python3.13 -m venv .venv
.venv/bin/pip install pymupdf==1.28.2
export PDF_PYTHON="$PWD/.venv/bin/python"
```

1. Create a PostgreSQL database and set `DATABASE_URL` in your shell or a private environment file. Never commit credentials.
2. Start the API from the repository root:

   ```sh
   PORT=5001 pnpm --filter @workspace/api-server run dev
   ```

   The API applies the idempotent initial SQL schema before listening. Portal tables are maintained in `lib/db/src/initialize.ts`; do not use `drizzle-kit push` to manage these tables. Future schema changes should be introduced as versioned migrations.

3. Start the UI in another terminal:

   ```sh
   PORT=5000 BASE_PATH=/ pnpm --filter @workspace/mockup-sandbox run dev
   ```

   Open `http://localhost:5000/`. Vite proxies `/api` to `127.0.0.1:5001`. Basic application flows need no provider credentials. Password reset emails require the configuration below; local testing uses the Google and Resend emulators.

4. Register your applicant account in the browser. To create an HRMO account, set `HRMO_EMAIL`, `HRMO_PASSWORD` (12–128 characters), and optionally `HRMO_NAME` in a private shell environment, then run:

   ```sh
   pnpm --filter @workspace/db run create-hrmo
   ```

   This requires `DATABASE_URL` and a running/initialized database. Existing accounts are not promoted or overwritten. Public registration always creates applicants.

Stop the foreground app processes with Ctrl-C. PostgreSQL data, accounts, documents, and sessions survive application restarts when the database volume is retained.

## Deployment

Build the packages, set `DATABASE_URL`, `PORT`, `NODE_ENV=production`, and `PORTAL_DIST_DIR` to the absolute path of `artifacts/mockup-sandbox/dist`, then run `pnpm --filter @workspace/api-server run start`. This serves the UI and API from one origin. Use HTTPS; production cookies are secure by default. `COOKIE_SECURE=true` also enables secure cookies in other environments.

This is an initial working application, not a completed university rollout. Before inviting real personnel, configure hosting and durable off-server backup storage, confirm official document/approval requirements, and establish account recovery and HRMO provisioning procedures. Email verification, general email notifications, university SSO, and malware scanning are not implemented. CSV applicant imports and HRMO-initiated password reset emails are implemented; production email delivery needs a configured sender. Uploaded files are private database objects delivered as attachments; validation checks size and file signatures, not malware. The login rate limiter is per API process; deployments with multiple instances need a shared limiter and a deliberately configured trusted proxy.

## Contract template and TOR workflow

New applications (`form_version=2`) follow the fields in `USTP Claveria Job Order Renewal for October to December 2026.pdf`, while preserving the eight-step navigation. First/middle/last/suffix fields produce the contract name; N/A middle names and suffixes are omitted. The USTP ID supplies the worker ID in the contract. The form does not collect nationality, so new contracts omit that phrase instead of inventing a value. The contract period comes from the selected start/end dates, TOR duties are automatically numbered, and the supervisor's entered position appears below their name. Rate words are derived consistently from the numerical daily rate.

All application encoding remains applicant-owned. HRMO has a read-only review, can approve/return an application, and can generate its PDF. **HRMO → Contract settings** supplies Chancellor/ID, HRMO director, Finance director and signing date for new forms. Settings use revision checks to prevent stale overwrites. Each generated PDF records the settings revision it used; changing settings affects subsequent generation, not existing downloads. The application must be returned for correction to change applicant details; this invalidates the old PDF.

Saved legacy applications retain `form_version=1`, their original fields, applicant-entered university signatories, and their structured weighted TOR. Their required fields and 100% section-weight validation are preserved. No legacy application is silently converted or its contract regenerated. New applicants choose from active offices; HRMO can add missing offices or deactivate/reactivate choices. The initial office directory comes from the supplied PDF and is seeded once; restarting does not reactivate disabled offices. Saved office names stay on existing applications.

`artifacts/api-server/src/contract/` contains the renderer and template assets derived from `JOB-ORDER-CONTRACT-TEMPLATE_Quarter4_2024.pdf`. Letterhead and acknowledgment preserve the supplied design; body text reflows on 612×936pt pages as TOR length changes. Legal clauses 4–11 preserve the supplied wording. Clause 2 uses the saved numbered TOR. One saved signing date replaces the sample's inconsistent October/July dates. All person names, addresses, IDs, pay, role, office, and contract dates come from saved records; sample employee details are not reused. Signatures and notarial entries remain blank. The PDF is generated locally with escaped input and stored in PostgreSQL; no external PDF service is called.

The API build copies Python/template assets to `dist/contract`. Ensure Python and PyMuPDF remain available in deployment, and configure `PDF_PYTHON` to their interpreter. A missing renderer produces a recoverable 503 response rather than a false successful download.

Additional verification:

```sh
"$PDF_PYTHON" artifacts/api-server/tests/contract-layout.py
# Optional directory argument writes a synthetic sample PDF and page images.
```

This checks Unicode and escaped input, all fixed legal clauses, page bounds, variable-length TOR pagination, signature grouping and the original acknowledgment page. The API suite also covers contract generation/download authorization, approval gating, and stale PDF invalidation, saved wizard position, complete applicant-owned contract details and rejection of HRMO field edits.

## CSV imports and account recovery

In **HRMO → Users**, upload a UTF-8 comma-separated CSV with exactly `name,email` headers (either order), up to 1,000 records / 500 KB. Quoted fields, UTF-8 BOM and CRLF are supported. Analyze first: each row is classified as new, existing, duplicate within the file, or invalid. The confirmation imports only valid new emails; it rechecks current database records and uses a case-insensitive unique index plus conflict handling, so concurrent imports never overwrite or duplicate users. Imports always create applicants, never HRMO accounts. Existing names, passwords and roles remain unchanged. Imported users have an unknown random password; HRMO sends them a reset email to choose their own password. Import itself sends no emails.

The existing server-configured Resend option uses:

- `RESEND_API_KEY`: a private Resend sending API key.
- `EMAIL_FROM`: the verified sender address (optional display name).
- `PUBLIC_APP_URL`: the actual HTTPS portal entry point used in reset links. Only localhost/127.0.0.1 development URLs may use HTTP.
- `RESEND_BASE_URL`: optional endpoint override for local testing; defaults to `https://api.resend.com`. Use only emulator credentials with a local endpoint.

Email configuration is server-only. HRMO can request a reset for any listed account; a reset email is limited to once per minute per user. Tokens are random, stored only as SHA-256 hashes, expire after 30 minutes and work once. Requesting a reset leaves the current password unchanged; completing it revokes all sessions. New requests invalidate older links. Provider failures return an error and roll back token replacement. Reset links use URL fragments, removed by the UI after receipt, so tokens do not enter server access logs. No password or reset token is returned through the management API. The API's authentication rate limit also applies to reset completion.

Local email verification uses CodeRabbit `emulate` release v0.0.1 with the `resend` service and its `/inbox` UI. Captured messages never leave the sandbox. Seed only synthetic data. In this task the private email env is outside the repository under the runtime directory; production still requires real sender credentials and an HTTPS public portal URL. The UI labels local delivery as preview mode. The provided Google Form mentions response-copy emails; those are not sent automatically by this implementation.

Administration tests (use the disposable API/database plus local email emulator):

```sh
TEST_API_URL=http://localhost:5002 node --test --test-concurrency=1 artifacts/api-server/tests/portal.test.mjs artifacts/api-server/tests/admin.test.mjs
```

Also set `DATABASE_URL`, `RESEND_BASE_URL`, `RESEND_API_KEY`, `EMAIL_FROM`, `PUBLIC_APP_URL` and `PDF_PYTHON` on the test process; the provider-failure test starts an additional temporary API on port 5003. The legacy suite marks only its synthetic fixtures as old-form records; administration tests exercise the new form, CSV races, office activation, permissions, contract settings/PDF generation, reset expiry/reuse, session revocation and provider errors.

## HRMO-managed Google email settings

HRMO can now configure Google email in **Email settings**:

1. Enable the Gmail API in the Google Cloud project. Configure the Google Auth Platform consent screen and audience (Internal when appropriate for the university Workspace organization; otherwise External with authorized test users during testing).
2. Create an OAuth client of type **Web application**. Copy the exact Authorized redirect URI shown in the portal. It is `{PUBLIC_APP_URL origin}/api/admin/email/google/callback`; do not substitute the API’s internal port for the public portal origin.
3. Enter the Client ID and Client Secret, save, and choose **Connect Google account**. Sign into the account that will send mail and authorize the requested permissions.
4. Send a test email to that connected account itself. Existing **Users → Send password reset email** actions then use Gmail automatically.

An API key, service-account JSON or Gmail password is not used by this integration. OAuth requests `openid`, `email` and `https://www.googleapis.com/auth/gmail.send`, with offline access. The sender comes from verified Google userinfo; HRMO cannot spoof a From address. External apps in Testing mode may have seven-day refresh-token expiry, and a Workspace administrator may need to permit the app. Consult [Google web-server OAuth guidance](https://developers.google.com/identity/protocols/oauth2/web-server) and [Gmail authorization scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) for production audience/verification requirements.

One-time server configuration:

- `PUBLIC_APP_URL`: the actual HTTPS portal entry point (HTTP accepted only for localhost/127.0.0.1 development). This controls both OAuth callbacks and password-reset links and is not editable by HRMO.
- `EMAIL_SETTINGS_KEY`: 32 random bytes encoded as 64 hexadecimal characters, supplied privately to the API process. Generate once, store outside the database/repository and retain securely across deploys and restores. Do not regenerate it on startup. Losing/changing this key requires re-entering Google credentials and reconnecting the sender.

Client secrets, refresh tokens and temporary PKCE verifiers are encrypted with AES-256-GCM using purpose-specific authenticated data. GET settings only reports the public client ID, connection status, sender and whether a secret is saved; no secret/token/ciphertext is returned to the browser. Settings changes use revision checks. OAuth states are hashed, expire after ten minutes, are single-use, and are bound to the initiating authenticated HRMO session and settings revision. The callback requires that same HRMO session. Access tokens are refreshed on send and held only in memory. Changing Google credentials requires reconnection; existing applicant accounts/passwords are unaffected.

Google provider failures are reported without automatically switching to another sender. Revoked grants are marked as needing reconnection. Disconnect removes the refresh token from the portal even if Google’s revocation endpoint is temporarily unavailable; the UI then advises removing the connection from the Google account as well. The optional **Use server-configured email service** action explicitly switches back to the server's Resend configuration. Test messages are limited to once per minute and sent only to the connected sender account.

For local testing, `GOOGLE_EMULATOR_URL` may point only to an HTTP localhost/127.0.0.1 CodeRabbit emulate v0.0.1 `google` service. The app overrides only its Google OAuth/token/userinfo/revoke/Gmail traffic. The sandbox's private strict-client seed is `/home/vercel-sandbox/runtime/emulate-config/google-seed.json`; environment configuration is in `google-local.env` and `email-vault.env` in the same directory. Use synthetic credentials only, and unset `GOOGLE_EMULATOR_URL` before entering real Google credentials. Local setup tests exercise OAuth + PKCE + refresh + raw MIME Gmail sends without delivering real mail. The UI clearly labels simulation mode.

`artifacts/api-server/tests/google-email.test.mjs` extends the API suite with protected settings, encryption/no-readback, OAuth session/state/revision/expiry/replay/scope handling, sending, password reset through Gmail, revoked grants and disconnect. Use the separate disposable database and strict seeded Google emulator; set `TEST_GOOGLE_CLIENT_ID`, `TEST_GOOGLE_CLIENT_SECRET`, `GOOGLE_EMULATOR_URL`, `EMAIL_SETTINGS_KEY`, `TEST_API_URL`, `DATABASE_URL` and `PUBLIC_APP_URL` for that test deployment. The private runtime wrapper `run-google-tests.sh` runs it together with the existing suites.

## Database backup and restore

Open **HRMO → Database backups** and enter your current HRMO password. **Download SQL backup** saves a PostgreSQL data-only `.sql` file to your browser's Downloads folder. It includes user accounts/password hashes, every application (including drafts), offices, review history, contract/email settings, uploaded files and generated PDFs. Take a backup before bulk changes and keep dated copies on secure storage outside the application server. Downloads are manual; this feature does not schedule off-server backups.

**Restore:** select a portal-generated SQL file, choose **Analyze backup**, check the backup date and table counts, then type `RESTORE` and choose **Replace records and restore**. This replaces current records, including accounts and passwords, with those in the file. Make sure you know an HRMO password from that backup. Active sessions, password reset links and in-progress Google authorizations are cleared; everyone signs in again after success. The stored Google sender credentials are preserved, but require the original server `EMAIL_SETTINGS_KEY` to work.

Safeguards and limits:

- Only authenticated HRMO users can access backups. Download, analysis and restore require password reauthentication; incorrect password attempts are limited per HRMO account/process. Use HTTPS in production.
- Portal files carry a format version, schema fingerprint and SHA-256 integrity checksum. The checksum detects accidental corruption, not a file's authorship. Only restore files from a trusted source. Analysis checks structure and counts; database constraints are checked during the restore transaction.
- The web restore parser accepts only this portal's generated data format. It never executes uploaded SQL; it binds parsed record values to fixed table queries. Arbitrary SQL scripts and `pg_dump` files require administrator tools below.
- All replacement happens in one PostgreSQL transaction. Failures roll back record changes. Before replacement, a complete SQL recovery copy of the current database is written and synced to private server storage. Failure to save that copy prevents restoration. **Recovery copies** lists these files for authenticated download, including copies created by unsuccessful restore attempts. To undo a restore, download its recovery copy and restore that file.
- Set `BACKUP_DIRECTORY` to an absolute private, persistent directory writable by the API account (for example `/var/lib/ustp/backups`). It must be outside the served web directory. The default is `.private-backups` relative to the API working directory and is ignored by Git. Files are created with mode `0600`; new directories use `0700`. For multiple API instances, mount the same private persistent directory on all instances. Copies are retained until an administrator archives/removes them; monitor disk usage. A server disk copy alone is not disaster recovery.
- PostgreSQL advisory locks coordinate restore with all portal requests across API instances. Restore fails with a retry message if any request is still active; during restore, new portal requests receive 503. Restore during a quiet period. Stop external SQL writers, workers and schema migrations first; they do not use the portal's request lock. The coordinator uses a separate pool of at most 20 database connections per API instance in addition to the normal application pool.
- SQL files and recovery snapshots are limited to 50 MB. Upload limits at your reverse proxy must allow that size. Larger databases require administrator `pg_dump`/`psql` tools. Backups restore only to a matching initialized portal schema; they do not contain schema definitions, roles, server environment variables, or external email provider state.
- Keep `EMAIL_SETTINGS_KEY` in separate secure storage. It is deliberately absent from SQL files. Without the original key, HRMO must enter Google credentials again and reconnect the sender after restoration.

### Administrator SQL dumps

For a full PostgreSQL backup, use PostgreSQL 17 client tools (a `pg_dump` version compatible with the server), an account with backup permissions, and private connection configuration such as `PGSERVICE`/`.pgpass` or environment variables. Never put credentials in a tracked file. The following examples use a privately configured `PGSERVICE=ustp`:

```sh
umask 077
PGSERVICE=ustp pg_dump --format=plain --no-owner --no-privileges --file=ustp-full-backup.sql
```

For disaster recovery, create a **new empty** database, configure a separate `ustp_recovery` service entry, then restore the trusted full dump there:

```sh
PGSERVICE=ustp_recovery psql --no-psqlrc --set=ON_ERROR_STOP=on --single-transaction --file=ustp-full-backup.sql
# Invalidate restored access tokens before serving requests.
PGSERVICE=ustp_recovery psql --no-psqlrc --set=ON_ERROR_STOP=on --command='BEGIN; DELETE FROM public.portal_google_oauth; DELETE FROM public.password_resets; DELETE FROM public.portal_sessions; COMMIT;'
```

Verify counts and documents in the recovered database before switching `DATABASE_URL` and restarting the API. Retain the old database until recovery is verified. Full dumps can execute SQL and must come from a trusted source. Portal-generated data-only SQL can also be run with `psql --no-psqlrc --set=ON_ERROR_STOP=on --file=portal-backup.sql` on a **matching initialized schema**, while all application instances and external writers are stopped; that file includes its own transaction and token cleanup. Take a separate backup first because command-line restores do not create the portal's automatic recovery copy.

Backup integration tests require their own disposable database ending in `_backup_test`, an API configured with that database, and a private `BACKUP_DIRECTORY` shared between the test process and that API:

```sh
TEST_API_URL=http://localhost:5005 node --test artifacts/api-server/tests/database-backup.test.mjs
```

Also supply `DATABASE_URL` and `BACKUP_DIRECTORY`. The suite deliberately replaces all records in this disposable database; never point it at a production database. It verifies SQL interoperability, exact binary/timestamp/bigint recovery, role/password checks, damaged-file rejection, rollback, automatic recovery and request coordination.

## Quarterly renewals with less encoding

Applicants can choose **New application → Reuse your previous application**, select an approved application, and choose **Reuse and start renewal**. The most recent contract period is selected initially; older approved applications are also available. The **Renew** button beside an approved application starts the same flow. A blank form remains available.

The new draft copies personal/education/contact details, position, daily rate, supervisor, office and TOR. It opens at **Contract** with blank start/end dates, so applicants enter the new period, adjust any TOR duties or changed information, and use **Review** before submitting. Completed sections can be revisited or skipped through the existing step navigation. Inactive offices are cleared for new-form renewals so a current office must be chosen. Existing form versions and their TOR layout are retained; a legacy form's signing date is also cleared and its other fields remain editable.

Each renewal has its own reference and starts as a draft with a fresh review process. The previous application, attachments, generated PDF and review history remain intact. Supporting files are not copied because they may be specific to the previous period. A new history entry identifies the source application. Repeated or concurrent Renew clicks reopen an existing draft/returned renewal from that source without overwriting edits. After that renewal is submitted, another renewal can be started. HRMO cannot create renewals on an applicant's behalf, and applicants cannot copy another person's records.

No database schema changes are required; the source relationship uses the existing application history and is included in SQL backups.
